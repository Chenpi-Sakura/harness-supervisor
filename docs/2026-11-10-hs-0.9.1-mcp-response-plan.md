## 0. 结论摘要

0.9.1 不重构 Worker 生命周期，也不改变事件落盘和 CLI 诊断能力，只改造 MCP 返回层：

1. 每一个实际注册的 MCP 工具都必须有 Production 与 Development 两套显式字段白名单。
2. Production 只返回完成当前决策和下一步操作所需的信息；Development 返回扩展诊断字段，但不是原始内部对象。
3. Production 的 `worker_status` 保持纯状态查询，不返回完整结果；`worker_wait` 在 Worker 完成时直接返回完整最终结果。
4. 两种模式都必须保留后续操作所需的 ID、游标和请求号。
5. 两种模式都不得返回凭据、环境变量和认证材料。
6. 0.9.1 的验收以逐工具契约测试、绕过测试、游标测试和响应体积实测为准，不以主观判断代替。

典型调用体验应为：

```text
worker_spawn -> worker_wait -> 处理最终结果
```

需要输入时：

```text
worker_wait（status=awaiting_input，返回 pendingInput）
  -> worker_answer
  -> worker_wait
```

不需要再通过 `worker_status -> worker_events -> worker_status` 拼凑结果。

### 0.3 Phase 5 实施状态：worker_list 真分页（2026-11-10）

已实施 Keyset Pagination：

- 排序键固定为 `(createdAt DESC, id ASC)`；同一毫秒创建的 Worker 由 id 决定稳定顺序。
- Cursor 在最外层 MCP 编码为不透明 Base64URL；内容是该页最后一条记录的 `createdAt + id`。IPC `list` 新增可选 `after` 键集位置，不依赖记录仍然存在。
- 删除/遗忘 cursor 指向的记录不会跳过其后续记录；分页过程中新增的更新 Worker 排在 cursor 之前，不会插入后续页；归档/删除尚未读取的记录只会按当前过滤条件消失，不会造成后续重复。
- MCP 每页请求 IPC `limit + 1` 条推断 `hasMore`，不再把 500 条读取上限伪装成完整历史。
- 旧 Daemon 不认识 `after`：第一页仍可用；带 cursor 的后续页在 MCP 层直接返回 `UNSUPPORTED` 并提示升级 Daemon，不会把旧严格 Schema 的原始报错暴露给调用方。升级 Daemon 后恢复分页。
- 新测试 `test/integration/mcp-list-pagination.test.ts`：1,200 个 Worker 全量翻页（12 页 × 100）核对顺序、无重复、无遗漏；并发新增 3 个、遗忘 2 个（含 cursor 记录）、归档 1 个后继续翻页；畸形 cursor 返回 `BAD_REQUEST`。

### 0.4 大结果策略（0.9.1 决定）

`worker_wait` 继续返回完整最终结果，不增加展示层截断。Worker 交付的研究报告、审计结论等属于 Master 验收所需的信息，不能为了节省上下文而丢弃；`result.truncated` 只表示 Supervisor 存储层已按 `maxResultBytes` 截断，不是 MCP 投影造成的。ResultRef / 大结果分段读取留待后续版本，不在 0.9.1 扩大范围。


| Runtime | spawn | wait | status | events | Development status |
| --- | ---: | ---: | ---: | ---: | ---: |
| Qoder 1.1.82 (ACP) | 536 B | 355 B | 406 B | 544 B | 7,211 B |
| MiniMax Code 0.7.0 (ACP) | 536 B | 355 B | 406 B | 544 B | 7,367 B |

两者均满足：

- `worker_wait` 返回完整 19 字符结果一次，`truncated=false`，无 `events`。

- 独立审查完成：无阻断项。根据审查补强：

  - `worker_list` cursor 要求规范 ISO 时间戳，非规范值返回 `BAD_REQUEST`，防止字典序错位。

  - `types:[]` 的等待回归改用 `[scenario:delayed-progress]`，确保修复前会失败。

- ACK 的逐 id `ackedIds`/`alreadyAcked`/`ackAtById`（IPC 只返回聚合 `acked` 与 `missing`）。
- `wake_target` 的 `previousTarget`/`validation`（IPC 不返回变更前目标与校验明细）；`updatedAt` 已返回。
- `worker_wait` 的 `scannedEvents`/`scanMs`/`waitMs`/`timeoutReason`/`lastEvaluatedSeq`（`WaitResult` 不提供这些字段）。

结论：Production 契约完整；未实现的仅是 Development 诊断增强，不影响 Master 主调用链，也不影响安全边界。全量回归与真实 Harness 验收通过，发布建议见 [0.9.1 交付报告](2026-11-10-hs-0.9.1-report.md)。

## 1. 背景与目标

近期实际使用中，Production MCP 的主要问题是把底层执行过程直接带回 Master：

- Qoder Worker 的 `run.progress` 可能按 token、单词或短片段产生；一次 `worker_events` 可能返回数百条无意义事件。
- `worker_wait` 超时后可能带回大量历史事件、`lastProgress` 和 `timeline`。
- `worker_status` 重复返回完整 Session、时间线和进度摘要。
- Development 目前直接返回内部 DTO，缺少自己的诊断字段白名单，未来新增字段会无意泄漏。

0.9.1 的目标是区分：

- **内部数据完整性**：HS 继续完整记录事件、Session 引用、通知投递和诊断信息。
- **外部信息展示粒度**：MCP 只把当前模式允许的字段投影给调用方。

### 1.1 必须保留的能力

- Persistent Worker 的 Worker 身份、Session 连续性和多轮 `worker_continue`。
- 多 Worker 并行、独立通知目标和 `needs_input -> answer -> continue`。
- Worker 崩溃恢复、事件完整落盘、通知 ACK 和事件 ID 语义。
- CLI 的完整诊断能力。
- Development 模式下的原始事件、完整时间线和投递诊断能力。

### 1.2 非目标

- 不重构 Worker 生命周期。
- 不引入 Task 调度系统、SQLite 或第二套状态存储。
- 不改变 Session 管理方式、ACK 业务语义或 Harness Adapter。
- 不删除底层事件日志，不改变 `events.jsonl` 的完整性。
- 不自动生成 Worker 工作总结。
- 不改变 Master 与 Worker 的任务粒度。
- 不允许通过 MCP 调用参数切换 Production / Development。

### 2.4 当前游标与事件过滤事实

- `store.readEvents()` 返回的 `nextSeq` 是本次从存储读到的最后一条事件的序号；没有事件时等于 `sinceSeq`。
- `hasMore` 表示存储侧是否还有更多事件。
- `context-budget.ts` 在读取之后再过滤 progress，因此严格游标读取时 `nextSeq` 已经跨过被过滤的 progress。
- 紧凑事件读取中：
  - `eventsOmitted` 表示被预算或条数上限丢弃的 lifecycle 事件；
  - `progressOmitted` 表示扫描窗口中过滤掉的 progress 数量；
  - 无 `sinceSeq` 时是从尾部向前扫描的快照，最多 3 页 × 300 条窗口；
  - 有 `sinceSeq` 时使用严格增量读取。
- `worker_wait` 默认 `until=terminal`，不会因为普通 progress 立即返回；但 `until=event` 配合 `types` 可以请求 progress。
- `worker_wait` 超时会读取最多 500 条事件，并附带 `lastProgress`、`timeline`、`inputState`。

## 3. 双模式定义

| 规则 | Production | Development |
| --- | --- | --- |
| 返回策略 | 严格字段白名单 | 扩展字段白名单 |
| 原始 progress | 禁止 | 允许 |
| Thinking 片段 | 禁止 | 允许诊断读取 |
| 完整事件 payload | 仅允许的生命周期事件，且只给摘要 | 允许 |
| Session 诊断 | `available` / `restorable` / `reason` 摘要 | 允许完整 Session 引用和诊断 |
| 进程信息 | 必要状态 | 允许 PID、进程诊断 |
| 内部错误 | 错误码、可理解信息、必要 ID | 允许错误码、详情和上下文 |
| 环境变量 | 禁止 | 禁止 |
| IPC 内部信息 | 禁止 | 允许非敏感诊断 |
| 历史投递记录 | 禁止 | 允许 |
| 返回体积 | 有固定预算和分页 | 有更大上限，但仍必须分页 |

### 3.1 两种模式都不得返回

- API Key、Token、密码、Authorization 头。
- SDK Auth Payload、IPC Authentication Token。
- 完整环境变量及认证信息。
- 私有凭证文件内容。
- Worker 的完整 prompt 或 `promptPreview`。
- 原始 Harness 认证报文和内部 IPC 报文。

字段白名单必须递归生效。不能只删除顶层字段，却让完整 Session、原始事件或投递记录从嵌套对象泄漏。

### 3.2 模式与参数边界

- Production / Development 由 MCP 进程启动配置决定，工具参数不能切换。
- Production 中请求被禁止的诊断面时，返回明确的 `UNSUPPORTED` 或 `BAD_REQUEST`，不静默返回原始数据。
- Development 也不等于“返回整个 DTO”；未列入扩展白名单的字段必须省略。

### 3.3 默认体积与分页

| 面 | Production | Development |
| --- | --- | --- |
| `worker_status` | 默认 ≤ 2 KiB；结果/错误/输入为有界预览（显式 `includeInput=true` 的面除外） | 可返回完整视图，但单一响应 ≤ 64 KiB 或明确分页 |
| `worker_events` | 默认 ≤ 4 KiB；快照最多 10 条 lifecycle | 单页最多 500 条或 256 KiB，超出时 `hasMore=true` |
| `worker_wait` 超时 | 只返回状态和游标，目标 ≤ 1 KiB | 可带扫描统计、时间线、进度摘要 |
| `worker_wait` 完成 | 完整最终结果，受 `maxResultBytes` 限制 | 同 Production，外加诊断字段 |
| `worker_list` | 默认 50，最大 200，必须分页 | 默认 50，最大 200，必须分页 |
| `supervisor_notifications` | 默认 50，最大 200 | 默认 50，最大 200 |
| `metrics_report` | 聚合结果；`includeTasks` 只给任务摘要 | 允许任务详情和字段覆盖，但分页 |

现有 `maxResultBytes` 默认为 64 KiB；结果被存储上限截断时，必须返回 `truncated` 或 `storedTruncated`，不得把截断文本伪装成完整结果。

### 3.4 必须保留的 ID 与游标

- Worker：`id`、`lastSeq`。
- 事件读取：`nextSeq`、`hasMore`。
- 输入请求：`requestId`；必要时带 `seq`。
- 通知：通知 `id`、`workerId`、`seq`。
- 度量：`taskId`、`usageId`。
- Persistent Worker：`persistence`、`lifecycle`、`session.available`、`session.restorable`。

### 3.5 accepted 与 completed 的边界

- `worker_spawn` / `worker_resume` / `worker_continue` 返回接受状态，不返回完成承诺。
- `worker_send` / `worker_answer` / `worker_cancel` 返回操作接受状态和当前状态。
- 只有 `worker_wait` 的 `terminal=true`、`worker_status` 的终态，或 `worker_events` 的终态事件，才表示运行结束。
- 不得把 `accepted=true` 写成 `completed`。

## 5. 设计取舍：worker_status 与 worker_wait

这是 0.9.1 最需要固定的调用体验。

### 5.1 Production worker_status

只做状态快照：

- 身份：`id`、`runtime`、`persistence`、`lifecycle`。
- 可用性：`session.available`、`session.restorable`、`resumeAvailable`。
- 当前动作：`status`、`pendingInput`、`lastSeq`、`lastEvent`。
- 结果面：`resultAvailable`、有界的 `resultPreview`、有界的 `errorPreview`。
- 不返回完整结果、完整事件、时间线、lastProgress、stderr。

### 5.2 Production worker_wait

承担等待和最终结果交付：

- 完成时直接返回完整最终结果，不再要求第二次查询。
- 失败/取消时直接返回终态和错误。
- 需要输入时直接返回 `pendingInput`，Master 可以立即 `worker_answer`。
- 超时只返回状态和游标，不返回历史事件和进度摘要。
- `until=event` 命中时返回允许的 lifecycle 紧凑事件。

### 5.3 推荐调用序列

正常任务：

```text
worker_spawn
  -> （若绑定唤醒）结束回合，等待通知
  -> worker_wait（终态，拿到完整结果）
  -> 处理结果
```

长任务且已绑定通知：

```text
worker_spawn
  -> 结束回合
  -> 通知唤醒
  -> worker_wait（无 sinceSeq，终态立即返回结果）
```

需要输入：

```text
worker_wait（awaiting_input + pendingInput）
  -> worker_answer(requestId)
  -> worker_wait
```

只有审计、排障或需要原始事件时，才调用 `worker_events`。`worker_events` 不再是拼装最终结果的主要路径。

### 5.4 兼容性说明

- Production `worker_status.includeResult=true` 返回 `UNSUPPORTED`，并提示改用 `worker_wait` 取完整结果；这是有意的行为变更，必须写入 CHANGELOG 和工具描述。
- Production `worker_status.includeInput=true` 保留，用于需要完整待处理输入后再回答的场景。
- Production `worker_status.recentEvents` 返回 `UNSUPPORTED`；需要事件请改用 `worker_events`。
- 依赖旧行为的自动化提示需要改为 `worker_wait` 取结果。

## 6. 事件过滤与游标规范

### 6.1 Production 事件类型白名单

允许：

```text
worker.starting
worker.started
worker.exited
worker.crashed
worker.orphaned
worker.interrupted
worker.resumed
worker.continued
worker.resume_failed
worker.admin
run.accepted
run.started
run.error
run.completed
run.failed
run.cancelled
run.needs_input
run.input_answered
```

不允许：

```text
run.progress
run.usage
worker.session
run.message_sent
未来新增但未列入白名单的类型
```

`run.progress` 包含但不限于：

- `thinking`（thinking 片段）
- `assistant_message`（流式助手文本）
- `tool_start` / `tool_end`
- `turn_complete`
- `context_usage`
- `permission_withdrawn`
- `session_init`
- 任何 token delta 或原始 Harness 流式片段

### 6.2 游标语义

统一定义：

- `nextSeq`：服务端本次已经检查过的最大事件序号，包括被过滤掉的事件。下一次查询从 `nextSeq` 之后继续。
- `hasMore`：在 `nextSeq` 之后是否还有未检查的事件（正向）。
- `eventsOmitted`：本次扫描到但未返回的 lifecycle 事件数量，通常由预算或条数上限造成。
- `progressOmitted`：本次扫描到但被 Production 过滤掉的 progress 事件数量。
- `lastSeq`：Worker 当前已知的最大事件序号，不等于本次响应返回的最后一条事件。

必须保证：

- 游标严格单调推进。
- 跳过 progress 不会导致重复扫描或生命周期事件丢失。
- 大量连续 progress 不会造成无限扫描或内存膨胀。
- 尾部快照和严格增量读取使用同一套游标定义。
- `hasMore` 真实反映正向剩余事件，不用它表示“历史中还有更早事件”。
- 无事件时 `nextSeq` 保持不变，不倒退。

### 6.3 扫描上限

- 尾部快照：最多 3 页 × 300 条窗口，最多 10 条 lifecycle 输出。
- 严格增量：单页默认 100，最大 200（Production）；Development 最大 500 条，256 KiB 硬预算未实现（依赖存储层单事件上限）。
- `worker_wait`：默认 30 秒，最大 120 秒；超时不继续扫描历史。
- 十万条连续 progress：必须能在有限时间内推进游标并返回，不得一次性构造完整数组。
- Worker 运行中持续产生 progress 时，`worker_wait` 不应因为 progress 反复返回空结果。

### 6.4 Production 参数绕过

以下请求不能突破 Production 过滤：

- `worker_events.includeProgress=true`
- `worker_events.seq=<progress seq>`
- `worker_wait.includeProgress=true`
- `worker_wait.types` 包含 `run.progress`
- `worker_wait until=event` 未指定 types 时，Production 只等待 lifecycle 允许类型；progress 不会结束等待
- `worker_status.recentEvents`
- `worker_status.includeResult=true`
- `supervisor_notifications.includeDelivery=true`
- 任何嵌套参数、`limit` 增大或 `state=all`
- 直接读取完整历史

Production 对显式诊断请求返回 `UNSUPPORTED` 或 `BAD_REQUEST`，并在消息中指向 Development 模式。不得静默返回原始数据。

## 7. 错误契约

### 7.1 工具错误

Production：

```text
CODE: 可理解的消息 (requestId=..., workerId=..., status=..., next=...)
```

- 保留 `code`、消息和后续操作所需的最少 ID。
- 保留 `CONFLICT`、`UNCERTAIN`、`INVALID_STATE`、`UNSUPPORTED` 等语义。
- 不返回堆栈、内部路径、环境变量或完整 details。

Development：

- 可以返回 `details` 对象、错误码、诊断上下文。
- 仍不得返回凭据和环境变量。
- 堆栈仅在经过脱敏且确有诊断价值时返回；当前实现未承诺返回堆栈。

### 7.2 Worker 失败

Worker 失败是正常响应，不是 MCP 工具错误：

```json
{
  "worker": { "id": "w-xxx", "status": "failed", "lastSeq": 140, "error": "失败原因" },
  "terminal": true,
  "timedOut": false
}
```

不得把 Worker 失败包装成 MCP `isError`，也不得把 `accepted=true` 写成 `completed`。

## 8. 实现结构

0.9.1 优先复用现有 `mcp-presentation.ts` 和 `context-budget.ts`，不新建第二套状态或响应服务。

建议职责：

```text
src/mcp.ts
  -> src/mcp-presentation.ts
       mode.ts            模式解析（已有）
       project.ts         通用白名单/递归投影
       worker.ts          worker_* 契约
       events.ts          事件白名单与游标
       notifications.ts   通知与 ACK 契约
       supervisor.ts      info/wake_target 契约
       metrics.ts         metrics_* 契约
       errors.ts          错误投影
  -> src/context-budget.ts
       预算、紧凑事件、预览、分页
```

实施要求：

1. 每种模式为每个工具定义显式 TypeScript 返回类型，不能依赖 `unknown` 或直接 `return dto`。
2. 投影函数必须递归生效，不能只删除顶层字段。
3. 事件策略集中定义，`worker_events` 和 `worker_wait` 共用同一白名单。
4. 所有工具（包括 `worker_forget`、ACK、metrics）都必须经过投影函数。
5. 所有新增字段先确认数据来源；没有持久化数据就不伪造。
6. 不改变 IPC 事件格式和 `events.jsonl` 完整性。
7. `worker_list` 分页可以在 MCP 层基于已排序列表切片实现，不强制改 IPC。
8. `worker_status` 的完整结果能力移到 `worker_wait`，不新增第二份结果存储。

### 11.1 输入兼容

- 不改变 CLI 输入和输出。

### 11.2 输出兼容

以下变化属于 0.9.1 的公开输出变更，必须写入 CHANGELOG：

- `worker_status` Production 不再返回完整结果、`recentEvents`、`timeline`、`lastProgress`。
- `worker_wait` 完成时直接返回完整结果；超时不再返回历史事件和进度摘要。
- `worker_events` Production 硬过滤 progress；`seq` 不能读取被过滤事件。
- `worker_list` 从数组改为带分页信封的对象。
- `supervisor_info` Production 移除 `limits`、`wake`、`storage`、runtime 完整备注；需要诊断时使用 Development。
- Development 不再返回原始 DTO，改为扩展白名单。

### 11.3 Daemon 兼容

- Production 仍要求 Daemon 满足现有最低 IPC 版本。
- 新字段（`workers` 计数、`sessionRestored`、`cancellationState`、`lastEvent` 等）在旧 Daemon 上缺失时，必须省略或标注未知，不得填假值。
- 不为了 0.9.1 修改 IPC 事件格式或状态目录结构。
- `worker_list` 分页在 Supervisor/IPC 层实现 Keyset 位置；MCP 负责编码不透明 cursor 和推断 `hasMore`，CLI 仍可使用原有 `list` 调用。
- 旧 Daemon 的严格 `list` Schema 不认识 `after`：无 cursor 的第一页仍可用，带 cursor 的后续页会返回其 Schema 错误；这表示该 Daemon 不支持完整分页，不能当作已完成遍历。

### 11.4 迁移说明

- 依赖 `supervisor_info.storage` 验证环境的脚本，改用 Development 模式。
- 依赖 `worker_status.includeResult` 取结果的提示，改用 `worker_wait`。
- 依赖 `worker_events includeProgress` 调试的流程，改用 Development 模式。
- 旧 MCP 客户端仍可调用，但 Production 的旧诊断旁路会被明确拒绝。

## 14. 最终原则

HS 是 Agent 的协作基础设施，不是向 Master 展示 Harness 内部运行细节的日志查看器。

Master 需要知道：

- Worker 是否接受任务。
- 是否正在执行。
- 是否需要介入。
- 是否已经完成。
- 最终交付了什么。

Worker 内部每一个 token、每一次 thinking、每一个底层协议事件，应由 HS 自己管理。Production 只传递决策所需的信息，完整执行过程留在 HS 内部；Development 通过扩展白名单提供可复核的诊断能力。
