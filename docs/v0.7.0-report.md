# Harness Supervisor v0.7.0 交付报告

- 基础版本：0.6.6
- 最终版本：0.7.0
- 日期：2026-11-04
- 分支：`main`（开发在临时分支完成，按项目规范 squash 合并）
- 生产升级：未在本轮执行；如需升级，先确认无活动 Worker
- 版本号：保持 0.7.0，不因默认切换升级版本

## 1. 本轮目标

为 Qoder CLI 增加官方 ACP 传输层，并在真实验收通过后**把默认传输切换为 ACP**：

```bash
# 默认 ACP；需要旧传输能力时显式回退
HARNESS_SUPERVISOR_QODER_PROTOCOL=stream-json
```

变量在 daemon 启动时读取，切换后需重启 daemon。ACP 只改变 Qoder Adapter 的
传输方式，不改变 Supervisor 的生命周期、事件、通知、任务度量或 CLI/MCP 接口。
ACP 缺少的 stream-json 能力（steer/follow-up、tools 白名单、`plan` 模式、
Token 用量）如实报告；需要这些能力的 Worker 应显式使用 stream-json。本轮
不升级版本号，0.7.0 保持不变。

## 2. 实施

### 2.1 传输选择与句柄

- `resolveQoderProtocol()` 读取 `HARNESS_SUPERVISOR_QODER_PROTOCOL`，接受
  `acp`（默认）与 `stream-json`；非法值在 daemon 启动时明确失败，不静默回退。
- ACP Worker 启动参数为 `qodercli --acp`，不再传 `--print` / stream-json 参数。
- ACP 没有暴露 Qoder 的会话文件路径，因此 HS 在 Worker 自己的 session 目录写入
  `qoder-acp-session.json`：首行是
  `{ type: "session", id, runtime: "qoder", protocol: "acp", cwd, models }`。
  会话内容仍在 Qoder 自己的存储中，`session/load` 重新附着。
- resume 按句柄类型分派：ACP 句柄只能由 ACP 传输恢复，stream-json `.jsonl`
  只能由 stream-json 恢复。传输不匹配时返回 `UNSUPPORTED`，不会伪造成同一个会话。
- 模型目录随句柄保存；即使 `session/load` 不重复返回模型列表，resume 仍能把
  显示名（例如 `DeepSeek-Flash`）解析为 ACP 模型 id（例如 `dfmodel`）。

### 2.2 ACP 能力

- `initialize` 声明 `protocolVersion: 1`、只读文件读取和
  `clientCapabilities.elicitation.form`。不声明 URL elicitation，因为 HS 没有浏览器
  交接面。
- `session/new` / `session/load` 后显式设置模式与模型：
  - 权限模式映射：`bypass_permissions -> yolo`、`accept_edits -> acceptEdits`、
    `dont_ask -> dontAsk`、`default -> default`、`auto -> auto`；
    `plan` 没有 ACP 等价模式，直接返回 `UNSUPPORTED`。
  - `thinking` 映射到 `reasoning_effort`：`off -> none`、`minimal/low -> low`、
    `medium/high -> high`、`xhigh/max -> max`；不支持的级别明确失败。
  - `model` 按模型 id 或显示名精确匹配；无匹配时返回可用列表，不静默使用默认模型。
- `session/request_permission` 映射为 `awaiting_input`（`select`），保留 Qoder
  原生选项标签与 optionId；回复复用原生 JSON-RPC id 和 optionId。
- `elicitation/create` 映射为 `awaiting_input`：
  - 单字段枚举 -> `select`；
  - 单字段布尔 -> `confirm`；
  - 单字段自由文本 -> `input`；
  - 多字段 -> `input`，答案必须是属性到值的 JSON 对象。
  URL elicitation 不支持，会以 `decline` 如实拒绝并记录非致命错误。
- `session/update` 映射为既有进度事件：assistant 分块、思考分块、工具开始/结束、
  plan、模式更新。`session/load` 的历史回放不写入新运行的进度或最终答复。
- `session/cancel` 用于取消；取消时先取消待回答的权限/提问，再等待 turn 结束。
- Agent 发来的 `$/cancel_request` 会撤回对应的权限或提问；HS 用完整的
  `permission:<id>` / `elicitation:<id>` requestId 清除 `pendingInput`，不会让
  Worker 停在已经无效的 `awaiting_input`。该路径由集成测试覆盖（真实 1.1.82
  验收中未触发撤销）。
- `session/prompt` 返回的 usage 在 1.1.82 中全为零，因此**不写 `run.usage`**；
  以后出现正数 token 时才按运行时报告记录。
- 工具白名单（`tools`）与 provider 在 ACP 下明确返回 `UNSUPPORTED`；ACP 没有等价
  控制项，不伪造支持。
- ACP 能力声明 `steer=false`、`followUp=false`。Qoder 在
  `initialize._meta.qoder.promptQueueing` 中声明了 prompt queueing，但 HS 尚未验证
  排队 prompt 对运行段边界的影响，因此不把未验证能力暴露给调用方。

## 3. 真实验收

环境：Windows x64、Node 24、`qodercli 1.1.82`、模型 `DeepSeek-Flash`。
使用正常 `~/.qoder` 登录态；验收脚本移除桌面注入的未认证 `QODER_CONFIG_DIR` /
`QODERCN_CONFIG_DIR`。命令：

```bash
QODER_REAL=1 QODER_REAL_MODEL=DeepSeek-Flash node scripts/e2e-qoder-acp.mjs
```

脚本不再设置 `HARNESS_SUPERVISOR_QODER_PROTOCOL`，因此这次运行直接验证新的
默认传输（ACP）。结果全部通过：

| 场景 | 结果 |
| --- | --- |
| ACP spawn + prompt | `completed`，结果 `QODER_ACP_E2E_OK` |
| ACP resume / `session/load` | `completed`，结果 `QODER_ACP_RESUME_OK`，session id 与句柄不变，`resumeCount=1` |
| Write 工具审批 | `awaiting_input` 暴露原生选项 `Allow for this session / Allow / Reject`；回答 `Allow` 后文件内容为 `ACP_WRITE_OK` |
| AskUserQuestion | `elicitation/create` 映射为 `select`，选项 `是 / 否`；回答 `是` 后结果 `QUESTION_YES` |
| 取消 | `session/cancel` 后状态 `cancelled`，进程已退出 |
| 非致命错误 | 各场景 `runErrors=0`、`fatalErrors=0` |
| Token 用量 | `usageEvents=0`（1.1.82 全零视为未知） |

证据：[`evidence/qoder-acp-real/`](../evidence/qoder-acp-real/)，包含
`result.json` 与投影后的 `events.jsonl`（不包含原始会话内容）。

- Qoder ACP 集成：**7/7 pass**（spawn/resume、权限允许与拒绝、elicitation、
  多字段、取消、错误、传输不匹配）。
- `qoder-launch` 单元：**8/8 pass**（含协议解析与 ACP 句柄识别）。

## 5. 已知限制

- 0.7.0 起 ACP 是默认传输；stream-json 仍可通过
  `HARNESS_SUPERVISOR_QODER_PROTOCOL=stream-json` 选择。默认 ACP 不提供
  steer/follow-up、tools 白名单、`plan` 模式和 Token 用量，需要这些能力时应
  显式回退。
- 1.1.82 的 ACP assistant 分块没有 `messageId`；HS 以工具调用为边界重置最终
  文本，工具之后的连续过程播报仍可能混入 `worker.result.text`。完整过程保留在
  事件中，不能仅凭结果文本断言它是唯一答复。
- 1.1.82 的 ACP usage 全为零，无法提供 Token 用量；不读取私有会话库。
- steer 与 queued follow-up 未实现；`promptQueueing` 只有上游元数据，没有 HS
  侧验证。
- `plan` 权限模式、工具白名单、URL elicitation 在 ACP 下明确不支持。
- HS 只代理 ACP `fs/read_text_file`（上限 5 MiB），不支持客户端写入；
  Qoder 自己的写入工具仍走原生权限请求。
- 入口与 daemon 的协议配置必须一致；切换
  `HARNESS_SUPERVISOR_QODER_PROTOCOL` 后，旧传输创建的 Worker 不能 resume，
  会得到明确的 `UNSUPPORTED`。
- 与所有 runtime 一样，`cwd` 不是文件系统沙箱；ACP 不改变这一边界。
