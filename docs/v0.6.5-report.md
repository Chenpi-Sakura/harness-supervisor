## 2. 问题修复情况

### 2.1 Worker 终态信息不完整（P0）

**原始问题**：Qoder 超时取消后，`worker_status(includeResult:true)` 只看到取消原因；最后有效进展在 `partialText` 事件里，需要再查 `worker_events` 指定 seq。

**根因**：
- 终态事件保存了 `partialText`，但没有在状态响应中提供结构化提取。
- Pi 在 abort 时会收到一条空的合成 assistant message，覆盖了 `lastAssistant`，导致取消时的 `finalText` 变为空；这是本轮新发现的关联缺陷。

**实施**：
- 新增 `src/progress-evidence.ts`：按“assistant 文本 > 工具输出 > 终态 partialText”的规则选取最后有效进展，跳过工具参数、空文本和纯生命周期事件。
- `worker_status` / `worker_wait` 新增 `lastProgress`：`seq`、`ts`、`source`、`evidence`、`chars`、`originalChars`、`truncated`、`storedTruncated`。`evidence=partial_progress` 明确不是验收。
- 完成状态不在 `lastProgress` 重复最终文本，返回 `textInResult=true`。
- Pi 修正：abort 合成空消息不再覆盖最后一条真实 assistant 文本。
- 默认状态仍受 2 KiB 预算约束；实测带全部新字段的取消状态 1302 bytes、完成状态 1137 bytes。

**修改文件**：`src/progress-evidence.ts`、`src/supervisor.ts`、`src/types.ts`、`src/context-budget.ts`、`src/mcp-presentation.ts`、`src/adapters/pi/session.ts`、`src/mcp.ts`、`src/cli.ts`
**测试**：`test/unit/progress-evidence.test.ts`、`test/integration/status-evidence.test.ts`（正常完成、取消 partial、重启、无有效进展、超预算）
**剩余限制**：只提取 HS 已存的文本；更长的原始输出在 Runtime session 文件中。工具日志不会被当作完成证据。

### 2.2 输入请求有效期与恢复体验（P0）

**先查明的事实**：
1. 5 分钟不是 Qoder 的协议限制，而是 HS 适配器 `PERMISSION_TIMEOUT_MS = 300_000`；超时后适配器会主动 deny。
2. Qoder 控制通道会一直等待回答；真实 1.1.79 在 5 分 58 秒后回答仍被接受并完成（`QODER_INPUT_OK`）。
3. Pi 的 `timeout` 由扩展提供，HS 原样转发；没有原生 timeout 时默认不设 HS 上限。可用 `HARNESS_SUPERVISOR_PI_INPUT_TIMEOUT_MS` 设置可选上限（取与原生 timeout 更短者），到期时 HS 向 Pi 发送 `extension_ui_response` cancelled。
4. MiniMax Code 默认 30 分钟，可用 `HARNESS_SUPERVISOR_MCODE_INPUT_TIMEOUT_MS` 单独覆盖。其宿主自身的等待上限仍未验证：真实 0.7.0 Ask 模式没有触发审批请求，因此只声明 HS 侧计时器可配置，不声称宿主一定能等待 30 分钟。
5. Worker 退出后原请求不可回答；Resume 只能在新进程中继续同一 session，不能把旧答案补交给已结束的请求。

**实施**：
- Qoder 默认窗口改为 30 分钟，`HARNESS_SUPERVISOR_INPUT_TIMEOUT_MS` 可配置（60s—24h）；适配器与 Supervisor 使用同一期限。
- MiniMax Code 同样默认 30 分钟；`HARNESS_SUPERVISOR_MCODE_INPUT_TIMEOUT_MS` 优先于通用变量，并补上 `~/.minimax-code` 独立安装目录探测。
- Pi 保留扩展原生 `timeout`，另加可选 `HARNESS_SUPERVISOR_PI_INPUT_TIMEOUT_MS` 上限；到期时 Supervisor 发送取消响应，避免最小 Harness 永久挂起。
- `worker_status` 新增 `inputState`：`pending` / `answered` / `expired` / `withdrawn` / `closed`，含 `expiresInMs`、`nextActions`；缓存视图每次读取刷新剩余时间。
- `worker_answer` 先校验参数形状，再检查状态；过期返回 `INVALID_STATE` + `reason=input_expired` + `nextActions=["worker_status","worker_resume"]`；重复回答返回 `already_answered`；Worker 已结束提示 `worker_resume`。
- 现存请求的 `requestId` 不匹配、取消中、答案在途都有各自 `reason`。
- MCP `worker_answer` 的 schema 使用 `superRefine` 在入口阻止 `value` + `confirmed` 同时传入；`cancelled` 只接受 `true`。
- Daemon 重启对账时清除旧的 `pendingInput`，保留事件证据，避免把已失去运行时的请求显示为可回答。

**修改文件**：`src/input-timeout.ts`、`src/input-state.ts`、`src/supervisor.ts`、`src/adapters/pi/session.ts`、`src/adapters/qoder/session.ts`、`src/adapters/mcode/session.ts`、`src/adapters/mcode/launch.ts`、`src/mcp.ts`、`src/mcp-presentation.ts`、`src/types.ts`、`src/cli.ts`
**测试**：`test/unit/input-state.test.ts`、`test/unit/input-timeout.test.ts`、`test/integration/qoder.test.ts`（默认 30 分钟、可配置 60s、真实等待）、`test/integration/status-evidence.test.ts`（过期、重复回答、互斥参数）、`test/integration/mcp.test.ts`（schema 拒绝）
**剩余限制**：Qoder 只验证了 AskUserQuestion 一次；MiniMax Code 的 HS 侧窗口可配置为 30 分钟，但宿主自身上限未验证（真实 0.7.0 Ask 模式未触发审批），不能把“HS 不提前拒绝”扩大为“宿主一定等待”。Pi 的可选 HS 上限只经过脚本化 Harness 与单元测试，没有真实扩展超时验证。请求过期不会自动批准，也不会重复执行副作用操作。

### 2.3 通知统计范围不明确（P0）

**原始问题**：按 Worker 查询通知时，列表只有 1—2 条，`counts.pending` 却是 7；调用方无法判断数字是当前筛选还是全局。

**实施**：
- `Notifier.counts(filter)` 应用与 `list` 相同的 state/worker/unacknowledged 规则（不含 limit）。
- `supervisor_notifications` 返回 `filteredCounts`、`globalCounts`、`scope`（state/workerId/limit/returned）；旧 `counts` 保持全局语义。
- MCP production 明确 `countsScope: "global"`；旧 daemon 未提供新字段时不把全局值错误标成 filtered。
- CLI `inbox` 同时打印 filtered/global 两组数字。

**修改文件**：`src/notify.ts`、`src/supervisor.ts`、`src/types.ts`、`src/mcp-presentation.ts`、`src/mcp.ts`、`src/cli.ts`
**测试**：`test/unit/notify.test.ts`（局部/全局/空结果）、`test/unit/mcp-presentation.test.ts`（旧 daemon 回退）、`test/integration/status-evidence.test.ts`（单 Worker、空结果）
**剩余限制**：`filteredCounts` 不包含被 limit 截断的记录数以外的信息；`returned` 与 `filteredCounts` 的差异需要调用方自行读取。未改 ACK、去重与投递机制。

### 2.4 原始事件截断与读取边界（P1）

**定位结果**：截断发生在两层：
1. 适配器对 assistant/tool 文本的 `safeText` 上限（此前 Pi/Qoder/mcode 的 assistant preview 为 400，Qoder tool result 为 300）；
2. Supervisor 入库时 `detail` 500 / `preview` 1000 的上限。

**实施**：
- 适配器 assistant/thinking preview 提高到 4000；Qoder tool result 4000、tool input 2000；mcode tool title 2000。
- Supervisor 进度入库 `detail` 8 KiB、`preview` 4 KiB；终态 `partialText` 4 KiB。
- 新增 `*Truncated` / `*Chars` 元数据；单条事件读取在 `storedTruncated` 时给出说明：只能返回 HS 已存内容，完整原文在 Runtime session 文件。
- 默认状态/事件读取仍按 2 KiB / 4 KiB 预算压缩，不因为入库上限变大而膨胀。
**修改文件**：`src/supervisor.ts`、`src/adapters/{pi,qoder,mcode}/session.ts`、`src/context-budget.ts`、`src/mcp.ts`
**测试**：`test/unit/context-budget.test.ts`、`test/unit/mcp-presentation.test.ts`、完整回归
**剩余限制**：超过入库上限的文本无法通过 `--full` 恢复；只能查 Runtime session 文件。

### 2.5 Resume 时间信息（P2）

**实施**：
- `WorkerRecord.firstStartedAt` 持久化，Resume 不再丢失最初开始时间；`startedAt` 保持“最近运行段开始”的旧语义。
- `worker_status.timeline` 提供 `firstStartedAt`、`currentRunStartedAt`、`endedAt`、`resumeCount` 和运行段（start/end/outcome/open）。
- 任务度量的 `timing.firstStartedAt` 与 `TaskWorkerMetrics.firstStartedAt/resumeCount` 同步；对恢复过的 Worker 明确警告 `runMs` 只覆盖最新段。
**修改文件**：`src/types.ts`、`src/progress-evidence.ts`、`src/supervisor.ts`、`src/metrics.ts`、`src/mcp-presentation.ts`、`src/cli.ts`
**测试**：`test/unit/progress-evidence.test.ts`、`test/integration/status-evidence.test.ts`、`test/unit/metrics.test.ts`
**剩余限制**：运行中的长任务只从内存窗口（500 事件）构建段；终态会按需回扫完整事件日志。`workerRun` 仍不是跨恢复段的总墙钟。

## 3. Codex 协作能力专项

### 3.1 v0.6.1 自动绑定采用什么机制？

Codex 0.161.0 每次 `tools/call` 在 `params._meta` 中携带：

- `threadId`
- `sessionId`
- `x-codex-turn-metadata.thread_id`（同一值）

MCP 只从**本次调用**的 `_meta` 提取 `threadId`，校验规范 UUID，并要求两个字段一致；不使用 daemon 环境、`CODEX_THREAD_ID`、最近会话或全局 Thread ID。没有可靠身份时退回显式目标或 daemon 默认，并给出警告。

### 3.2 未显式指定目标时是否真实可靠？

在已记录的 2026-10-28 Codex Desktop 双对话实测中：两次 `worker_spawn` 均未传 `notifyTarget`，均返回 `source=caller`、`wake=bound`，目标分别是两个不同的 Thread；完成通知分别到达并被实际唤醒处理，未串线。本轮重新运行了自动化覆盖（同对话多 Worker、显式目标优先、无/非法身份降级、resume 保留、重连与 daemon 重启），全部通过。

**边界**：那是单次 Desktop 实测，不覆盖所有 Desktop 版本/休眠/卸载场景；`_meta.threadId` 是宿主提供的路由提示，不是认证边界。

### 3.3 双会话并行测试是否通过？

是。2026-10-28 真实 Desktop A/B 双对话通过；本轮没有再次安排 Desktop 人工测试，只回归自动化与既有证据。两个 target 不同，通知未串线。

### 3.4 `codex queue` 目前具备什么语义？

- 使用官方 `codex queue --thread <id> --message <text>`，消息写入 Codex 的队列存储，由目标 app-server 消费为后续消息/新回合。
- 投递是 at-least-once；`delivered` 只表示队列接受，不表示主 Agent 已读或被唤醒。
- 没有 `expectedTurnId`，不能保证进入**当前**活动回合；因此不是 steer。

### 3.5 `turn/steer` 在当前宿主中是否真实可用？

- **协议层**：可用。`TurnSteerParams` 需要 `threadId`、`expectedTurnId`、`input`。
- **受控 app-server 真实回合**：错误 `expectedTurnId` 被拒绝；正确 steer 被接受；模型最终文本包含 `HS_STEER_TOKEN_065`；回合结束后 steer 返回 `no active turn to steer`。
- **Codex Desktop 当前回合**：不可用。Desktop 的 app-server 是私有 stdio 进程（无外部 `--listen`）；共享 managed daemon 的 `loaded/list` 为空，第二个 app-server `thread/resume` 报 `already has an active writer`，`turn/steer` 报 `thread not found`。

### 3.6 v0.6.5 是否实现了 steer？

**没有实现宿主实时 steer。** 没有新增 steer 传输通道，没有写 `queue_1.sqlite`，没有读取 Desktop 私有文件猜测活动回合。`supervisor_info.codexSteer` 明确返回：

```json
{
  "status": "unavailable",
  "verified": { "appServerRpc": true, "modelApplied": true, "desktopActiveTurn": false },
  "reason": "Codex Desktop owns its thread in a private stdio app-server; the shared app-server refuses an active writer. codex-queue remains the supported delivery path."
}
```

### 3.7 未实现的技术阻塞与已做验证

- Desktop app-server 无外部控制端点；
- 共享 daemon 无法接管有活动 writer 的线程；
- 没有可靠方式从独立 daemon 取得 Desktop 的活动 `turnId` 并连接其 app-server；
- 已验证：schema、真实 RPC、错误 turn 拒绝、模型实际应用、完成后拒绝、跨进程 writer 锁、managed daemon `loaded/list` 为空、Desktop 进程拓扑。
- 详见 `docs/codex-steer-261030.md` 与 `evidence/v0.6.5-261030/`。

### 3.8 是否存在串线、误引导或重复执行风险？

- 自动绑定：按调用 `_meta` 取身份，目标按 Worker/事件持久化；双对话与重启测试通过。风险仍是宿主提供错误身份或投递重复，属于 at-least-once 边界。
- steer：未实现，因此不存在 HS 发起的误引导；queue 仍可能与后续回合合并或在宿主未加载时滞留，已在文档中说明，不把它描述成 steer。

## 4. 效率改善证据

| 指标 | 改动前 | 改动后 | 证据 |
| --- | --- | --- | --- |
| 终态诊断所需调用 | `status` + `events(seq)`（≥2 次） | 一次 `status` 得到 `lastProgress`（含 seq/时间/部分/最终标记） | `status-evidence` 取消与完成用例 |
| 输入过期后的失败调用 | 观测序列出现两次失败调用 + 再 resume | 一次 `status` 得到 `inputState=expired` 与 `nextActions`；一次 `worker_answer` 得到结构化 `input_expired` | `status-evidence` 过期用例 |
| 通知计数的歧义 | 局部列表 + 全局数字，需额外查询或猜测 | 一次响应含 `filteredCounts`/`globalCounts`/`scope` | `status-evidence` 单 Worker/空结果用例 |
| 默认状态输出 | 2 KiB 预算 | 仍 ≤2 KiB；带全部新字段的取消状态实测 1302 bytes，完成状态 1137 bytes | `context-budget` 与本地测量 |
| Resume 可读取信息 | 只有最近 `startedAt` | `firstStartedAt` + 每段 start/end/outcome + resumeCount | `status-evidence` 恢复用例 |
| Qoder 输入等待 | 5 分钟 | 30 分钟默认，可配置；真实 5 分 58 秒回答成功 | Qoder 真实证据 |

没有测量 Token 节省率；以上只统计调用次数、结构字段与响应大小。

## 6. 最终评价

- **是否比 0.6.1 更省心**：是。终态一次状态即可看到最后有效进展；输入过期有明确原因和下一步；通知计数不再误导；Resume 时间线可读；默认输出仍受限。
- **是否减少不必要的工具调用**：是。终态诊断从 status+events 降为一次 status；过期/重复回答不再靠多工具试错。没有用 Token 估算代替调用计数。
- **是否保持 Keep Simple**：是。没有新增服务、数据库、第二套消息队列或通知 Broker；新字段都从现有事件派生，没有重写生命周期。唯一新增的是两个小型派生模块（progress-evidence、input-state）和一个超时解析器。
- **虽然能改但没必要**：
  - 为 Desktop 强行写 `queue_1.sqlite` 或私有大 socket（不稳定、破坏隔离）；
  - 为 Resume 建第二套运行段持久化状态（事件已足够）；
  - 为 MiniMax Code 统一改 30 分钟（未验证宿主上限）；
  - 重新引入 Codex Hook 或常驻轮询。
- **下一阶段最值得关注**：如果 Codex Desktop 提供受支持的本地控制端点，优先补 host steer；否则继续完善 Worker 侧通知/输入语义，而不是增加新 Runtime 或复杂审批平台。
