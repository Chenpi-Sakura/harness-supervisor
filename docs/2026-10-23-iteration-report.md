## 实际实现

| 范围 | 行为与结论 |
| --- | --- |
| Worker 路由 | CLI `--notify-thread` / `--notify-none`；MCP/IPC `notifyTarget`。创建时持久化，重要事件与通知各保存历史目标。修改全局默认值只影响新 Worker。 |
| Resume 与接管 | 省略目标保留绑定，显式 `notifyTarget` 代表授权接管，仅影响之后事件；历史通知不会改投新接管者。 |
| 安全回退 | 新 Worker 无目标、旧 Worker 无绑定、旧通知无历史目标时保留收件箱。无“最近 Session”扫描，无共享 MCP 进程环境的自动身份推断。 |
| 请求幂等 | 副作用前等待准入日志写入，写入错误向上返回；完成与失败确认写入。修复日志压缩与并发新增/更新/释放的竞态及坏尾行粘连问题。 |
| 长期事件 | 每 Worker 缓存最近 500 条；启动流式扫描、完整历史异步分页、稀疏字节索引、通知单次扫描重建。追加过程中维护索引。 |
| 历史完整性 | 统一 UTF-8 字节上限并兼容旧中文大事件；识别已确认序号缺口和日志缺失。追加失败留下独立错误标记，普通 flush 报错不会把缺损历史变为“已恢复”。单个损坏历史不阻断其他 Worker 的控制。 |
| 通知可靠性 | 记录落盘确认后才调用宿主；原目标重试、ack 去重、旧记录保守回退、无换行坏尾恢复。仍为 at-least-once，外部接受与本地结果持久化之间仍可能重复。 |

本机真实 Codex shell 提供 `CODEX_THREAD_ID`，两个接收会话分别读取自身环境并显式传递。官方 [MCP 配置文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) 描述进程环境传递，并未在本次研究中建立逐请求 Thread 身份保证。因此 MCP 要求显式参数；没有可信 ID 就使用收件箱。此结论只描述本次核查范围，不声称其他宿主永远不支持上下文。

## 开发协作与审计修复

通过独立 HS Daemon 启动两个真实 Pi 开发 Worker，分别处理幂等日志和事件缓存；负责人直接开发路由，通过 HS `send` 反馈审计发现。初次 Pi 启动因沙箱无法访问现有配置锁失败，获准访问后重新启动成功。两个开发 Worker 最终触及预设 15 分钟上限而取消，已落盘的改动由负责人接手修复、核验并提交，没有把取消状态当完成声明。

独立审计的具体问题及修复：

1. 幂等 compact 在等待替换期间遗失新请求或更新：快照移入串行写队列，保留期间新增记录；完成/失败用新对象替换记录，避免引用型“快照”跟随原地修改而误删。
2. 崩溃半行吞掉下一条准入标记：追加前修复行边界，幂等和通知日志均有回归。
3. 中文事件字符上限与读取字节上限冲突：新写入按字节限制，旧合法大行兼容恢复；丢弃不可读行有警告。
4. 后续复审补充：历史追加错误不能被普通 flush 消费后悄然消失；重启时缺失已确认日志或序号缺口须明确报错。

## 兼容性、限制与升级判断

- CLI、MCP、IPC 仍接受旧参数；Worker/事件/通知新增可选字段，旧记录可加载。全局目标变为新 Worker 默认快照，旧记录不自动追随，这是避免跨会话误投的有意行为调整。
- 直接使用库的客户端需要迁移：`Supervisor.events()` 改为 Promise；`Store.getEvents()` 只返回缓存并报告 `truncated`，完整读取用异步 `readEvents()`。这项变化已在 README 明示。
- 既有 P2：`wait(until:'event', types:...)` 只检查游标后的前 500 条；目标位于后页且 Worker 仍运行时可能超时。应推进事件游标；不宣称已修复此限制。
- 通知仍可能重复；ack 不等于外部宿主读回执，也不撤回已经进入 Codex 队列的消息。公开 `codex queue` CLI 未提供本次可用的撤回接口，未修改宿主私有数据库。
- Qoder 的协议/生命周期回归通过，**本轮未重跑真实 Qoder E2E**；已有真实证据中 steer/follow-up 未生效的限制保留，不能从 fixture 测试推出真实能力可用。
- 事件文件、Worker 元数据、通知元数据和稀疏索引仍需现有 prune 保留策略，不承诺总磁盘或总元数据内存恒定。未增加新服务或强制协作流程。
- 不提供断电 fsync、磁盘损坏恢复或 exactly-once 保证。损坏历史不会自动补造丢失事件。

**可以进入受控升级审阅，但本轮没有执行升级。** 两个测试 Daemon 已确认关闭，六个真实 E2E Worker 均完成；开发 Worker 的失败/取消通知已 ack。末次只读检查原生产 IPC 返回 ENOENT，不能据此断言原 Worker 已退出或生产状态可直接迁移。升级前必须核对旧进程/Worker、备份状态，再停旧实例、启动新实例；回退时使用旧代码和备份状态。尤其不要把未知状态自动重跑。
