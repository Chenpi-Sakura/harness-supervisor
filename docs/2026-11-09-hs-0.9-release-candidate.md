### 6.3 关键说明

- 初始回合与 continue 回合都只调用一次 `worker_spawn` / `worker_continue` 后立即结束；没有 `worker_wait`、`worker_status`、`worker_events`、sleep 或轮询。
- Stage 2 第一次 needs_input 由 Master 选择 Reject，验证了 answer → 同一 Worker 继续 → completed → 再次唤醒，但没有验证允许写入；随后用显式 `value="Allow once"` 重试，外部文件真实创建并写入 `RC_DSH_OK`。
- 第一次 Allow 重试时，Master 同时传了 `value` 和 `confirmed`，`worker_answer` 按 Schema 返回 `Provide exactly one of value, confirmed, or cancelled=true`；这是预期的参数校验，不是 HS 状态错误。改为只传 `value="Allow once"` 后成功。
- 所有 8 条通知的 `target.codexThreadId` 均与所属 Thread 一致，`workerId#seq` 唯一，ACK 后未重复投递。
- Stage 3 的 Thread 切换 / 卸载 / 完整退出本轮没有新增证据；报告只沿用既往验证结论，不把本轮 Stage 1/2 的结果扩展为 Stage 3 已通过。

## 14. 升级与回滚

升级步骤：

1. 备份状态目录（至少 `worker.json`、`events.jsonl`、`notifications.jsonl`、`sessions/`）。
2. 确认活动 Worker；`daemon down` 会取消活动 Worker，先处理或等待其完成。
3. 替换构建与 CLI/MCP 入口；保持同一状态目录。
4. 启动新 Daemon，检查 `daemon.log` 的 `Supervisor initialized`：`warnings`、`checkpointed/scanned`、`storeInitMs`。
5. 抽查 `list`、`status`、`events`、`inbox` 与一次 `continue` / `resume`。

回滚步骤：

1. 停止新 Daemon，恢复上一版构建与入口。
2. 如未使用 `compact`，直接使用原状态目录；新增字段会被旧版本忽略。
3. 如已使用 `compact`，旧版本可能把保留缺口报告为历史断档；优先恢复升级前备份。
4. 回滚不涉及 native session 删除；session 文件在两个版本中都保留。
