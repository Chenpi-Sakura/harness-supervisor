# 长任务 Worker 的诊断、续派与验收 SPEC

## 目标与范围

让 Master 在跨机器长实验中快速判断任务是否继续运行、是否需要纠偏、结果是否符合验收条件。HS 管理 Worker 生命周期与证据关联，实验命令、阶段划分和验收标准仍由任务决定。

独立 Node HS 的本机日志在 11 月 20 日北京时间 01:02 和 12:55 记录了同版本 daemon 重新启动和 Worker 中断。12:55 的九秒内启动了三个不同 PID。两段均缺少旧 daemon 的正常关停记录，退出原因未知。远端实验进程的状态也无法从 `worker.interrupted` 推断。已实测绑定 `codex-queue` 的完成通知可以唤醒当前 Codex 会话，运行中 Worker 的通知改绑暂停。

按下列顺序交付。各项可独立验收。

## 1. 补齐 daemon 生命周期日志

**需求**

- 复用现有 `daemon.log` 和 daemon 启动时的输出日志。每次启动使用可关联的标识，记录时间、版本、实例、daemon PID、父进程 PID 及可取得的进程启动时间。区分进程进入入口、取得锁和 IPC 就绪，新客户端重连可用实例时沿用原 daemon 的身份。
- 记录开启新 daemon 的触发原因，以及启动失败或锁冲突的结果。能从现有锁或运行时状态读取旧实例身份时，记录旧 PID 与进程核对结果，区分已退出、PID 复用和无法核实。诊断逻辑沿用现有进程判定，日志字段不参与新的抢锁决策。
- 正常关闭、主动升级、宿主关闭、信号、未捕获异常和强制退出路径应在可记录时留下退出请求原因及最终结果。复用日志刷新机制，确保主动退出前关键记录有机会落盘，关闭超时仍有界。突然消失且缺少退出记录时，下一次启动可记录观察到的断点，退出原因保持未知。
- 恢复时用同一次启动标识关联 `worker.interrupted` 或 `worker.orphaned`，保留旧 Worker 状态、核对到的进程身份和判定结果。日志保持低频，只记录生命周期转折、失败与必要的关联信息。禁止记录凭据、完整命令行、环境变量或任务正文。

**验收**

- 用 Windows 隔离实例验证正常停止后重启、客户端遇到已有 daemon、启动失败、受控升级及测试进程突然退出。仅看日志即可区分启动尝试与 IPC 就绪，并从 Worker 恢复事件追到对应 daemon 启动。
- 模拟突然退出时允许缺少旧进程的退出日志，新的日志应如实记录已知事实。生产实例上本次只增加可观测性，历史退出原因留待新证据。

代码入口见 [daemon](../src/daemon.ts)、[IPC 客户端](../src/ipc/client.ts)、[启动对账](../src/supervisor.ts) 和 [日志实现](../src/util/logger.ts)。

## 2. 给不支持 steer 的 Harness 提供明确的纠偏路径

**需求**

- MCP 的 `worker_send` 在不支持 `steer` 时继续明确返回不支持，并用简短提示给出替代操作。Master 明确决定停止时，可对持久 Worker 调用 `worker_cancel`，确认当前回合停止后，再对同一 Worker 调用 `worker_continue` 并传入修正指令。
- 复用现有 `cancel` 和 `continue`，避免引入新的生命周期操作。普通发送不触发取消。持久会话无法恢复时应明确返回原因，由 Master 决定如何接手。
- 续派前先确认独立命令或远端作业的状态。归档路径纠偏优先在阶段边界进行，交代新路径与已完成的工作，避免重跑原命令。

**验收**

- 模拟不支持 `steer` 的运行时，发送消息应给出替代路径且 Worker 仍在执行。明确取消后，续派使用相同 Worker ID 和原生会话 ID，替代指令只接受一次。
- 覆盖无法恢复会话的分支。复用已有 [取消后同会话续派集成用例](../test/integration/persistent.test.ts#L119)。若修改 DSH 适配行为，须在真实 DSH 验证。

## 3. 每轮交一份结构化结果清单

**需求**

- Master 可在派单中请求结构化清单，并列出验收所需字段。使用一份版本化的结构化结果与具体 Worker 和回合关联，支持简短结论、实际输入及配置、预期与实际采用的门槛、逐条结果或明细文件引用、异常、产物引用和可获得的作业退出码。大批量明细放在产物中，MCP 返回摘要和引用。
- `worker_wait` 和 `worker_status` 从同一份已持久化结果中读取。现有纯文本结果保持可用，长报告按需查阅。对明确提交的结构化数据做校验和大小限制，任意模型文本不作为已验证数据。只接受与当前 Worker 和回合对应的结果，提交重试避免产生重复清单。
- 区分 Worker 自述与执行侧证据。作业退出码来自实际运行记录，缺失时为未知。退出码为零只代表已观测命令正常退出，产物和门槛仍需单独验收。

**验收**

- 用错模型分位点的例子验证。Master 请求一个门槛，Worker 报告使用另一个门槛。两者在同一份结果中分别可见，调用端能判断不一致。覆盖缺少退出码、输入不合法、重复提交、超大逐条结果和旧版文本结果。
- 同一 Worker 连续两轮时，每轮只关联各自的结果。重启后可以查回已经完成的清单，旧清单不会覆盖新一轮的结果。

现有结果定义和 MCP 展示见 [WorkerResult](../src/types.ts#L167) 与 [MCP 结果格式](../src/mcp-presentation.ts#L84)。

## 4. 断线后对账远端实际作业

**需求**

- 对显式关联的长作业，在启动或接管监控时记录稳定的作业标识、执行位置、所属阶段、Worker 与回合、预期产物及执行端证据位置。执行端提供可复核的作业状态与最终退出记录。单独的 PID 只在同一主机且能确认进程身份时可用作证据。
- Worker 状态与作业状态分别报告。可用证据支持时，告诉 Master 作业仍运行、已成功退出待验收或已失败。证据缺失、过期或指向其他作业时显示未知，并指出待核查的阶段。中断后复用同一作业标识恢复观测。HS 不自动重放启动命令，不因恢复会话而声称已接管远端进程。
- 第一版复用既有任务和状态存储。由具体任务提供作业标识和执行侧记录，避免引入新的远端管理服务、通用 SSH 调度器或高频轮询。保持现有重要事件通知的触发方式。

**验收**

- 先用隔离环境构造独立作业，在运行中重启 Supervisor。恢复后应能用同一个作业标识继续监控，只出现一次作业启动，并能收回真实退出码与产物引用。
- 覆盖已经退出、执行端不可达和旧证据指向不同作业的情况。至少用一次独立执行进程验证 `worker.interrupted` 与实际作业状态可不同。若只有模拟远端证据，应在交付时注明。

## 交付与审查

- 用「一轮完整对照」做验收样例。Master 给出输入、变量、命令和验收条件，Worker 从启动跟到退出，交回一份短清单和原始产物引用。该粒度是示例，由 Master 自行决定是否采用。
- 核心变更需验证 CLI 和 MCP 行为一致。代码审查重点检查日志脱敏、进程身份、状态持久化、取消与续派竞态，以及恢复路径是否可能重复启动作业。报告应区分真实验证、模拟测试和未验证项。
- 当前反馈支持减少串行等待、降低 Master 处理过程日志的负担，以及方便独立复验。缺少 Master 和 Worker 完整 token 记录及单人基线，本轮不以节省总 token 作为验收指标。
