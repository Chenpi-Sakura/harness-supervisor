# HS 0.9 架构可行性评审

- 日期：2026-11-09
- 评审基线：`main@7649b34`（0.8.0）
- 输入：`HS 0.9 Architecture Proposal`（2026-11-09）
- 性质：针对当前代码的可行性评审。本轮不修改运行时代码，也不把提案中的目标能力当作已实现。

## 1. 结论

| 提案中的关键问题 | 结论 | 主要依据 |
| --- | --- | --- |
| 现有 Worker Timeline 和事件序列能否无损迁移到 Run 模型？ | 事件序列可以无损保留；Run 视图只能确定性重建，不能声称无损。 | `seq` 单调且可原样保留；但启动失败、Resume 失败、进程退出关联和旧记录缺失字段不在现有 run 段语义内。 |
| Pi、Qoder、MCode、DSH 分别能提供哪些真正可用的原生 Session 操作？ | 四个运行时都只有“创建 + 恢复”经过 HS 真实验证；List、Inspect、Delete、Archive、Fork 均未达到可交付标准。 | Qoder 与 DSH 只由 `initialize` 声明了部分能力，HS 尚未调用或验证；MCode 只验证了 `session/load`；Pi 没有原生列表接口证据。 |
| Session Lease 和自动 Detach 能否在现有进程管理模型中可靠实现？ | 自动 Detach 可行性高，运行资源释放已经存在；Lease 只在“同一 daemon + 新增 Session 接管”的范围内可靠，跨 stateDir 的全局独占无法保证。 | 终态路径已经关闭 Harness 进程并移除 Runtime；daemon 锁只覆盖单 stateDir；PID 身份核验可以直接复用。 |

总体判断：提案的职责划分方向成立，但有三处前提需要修正后才能作为 0.9 的实施基线：

1. Run 迁移必须定义 `legacy` 与 `unknown`，不能把重建结果描述为无损。
2. AttachmentState 应由现有状态派生，不能成为第二份持久化真相。
3. Session Lease 必须与 `session_attach` 同期实现，并且只能承诺单 daemon 范围。

- Qoder 的原生 Session 可能位于不同的配置根目录（`src/adapters/qoder/launch.ts:246` 的 `qoderConfigRoots`）。仅凭 `sessionId` 不能证明两个引用指向同一个原生会话。

## 3. 问题一：Timeline 与事件序列迁移到 Run

### 3.1 当前语义

现有代码没有持久化的 Run 实体。一次“运行段”由以下事件间接表达：

- 起点：`run.accepted`（`src/progress-evidence.ts:160`）。
- 终点：`run.completed`、`run.failed`、`run.cancelled`、`worker.crashed`、`worker.interrupted`、`worker.orphaned` 中的一种（`src/progress-evidence.ts:177` 附近的映射）。
- 每次 Resume 接受后追加 `worker.resumed` 并增加 `resumeCount`。
- 历史段在读取时由事件重建，最多返回 20 段（`src/supervisor.ts:1117`）。

### 3.2 可以无损保留的部分

| 数据 | 结论 |
| --- | --- |
| 事件序号 | 可以。`seq` 是每个 Worker 内单调递增的整数（`src/store.ts:512`），迁移不得重编号。 |
| Run 的起止事件与时间 | 对存在 `run.accepted` 的段可以精确恢复，`startSeq` / `endSeq` / 时间戳都在事件中。 |
| Run 的终态 | 可以把六种终态事件直接映射到 Run 状态。 |
| 每轮最终文本与错误 | 完成、失败、取消事件携带文本或错误；`run.error` 与 `worker.exited` 提供补充证据。 |
| Usage 记录 | 现有 `runtime:<workerId>:<seq>` ID 与 Usage 文件可以保持不变；新增 `runId` 只能作为属性，不能重写 ID。 |

### 3.3 不能无损重建的部分

| 缺口 | 原因 |
| --- | --- |
| 启动失败 | `failStartup` 写 `run.failed` 且 `stage=startup`，但没有 `run.accepted`（`src/supervisor.ts:1852`），因此没有 run 段。把它补成 Run 属于新增语义。 |
| Resume 失败 | `worker.resume_failed` 没有对应的 `run.accepted`，且不会增加 `resumeCount`；把它补成一次 Run 会改变现有计数。 |
| 未接受 prompt 的崩溃 | `worker.crashed` 的 `stage=startup` 同样没有 run 段。 |
| 每轮 PID / 退出码 | Worker 记录只保留最近一次；事件里有部分证据，但崩溃路径的事件顺序需要启发式关联。 |
| 旧记录字段 | 早期记录可能没有 `firstStartedAt`、`resumeCount` 或完整的 `worker.session` 事件；无法推断缺失值。 |
| 损坏或断档历史 | Store 已能检测断档并拒绝把不完整历史当作完整历史（`src/store.ts:170`）。迁移必须保留该警告，不能用推测补齐。 |

### 3.4 结论

建议把“无损”拆成两个目标：

- **事件层无损**：保留 `seq`、原始事件文件、通知 ID 和 Usage ID，不做重编号。
- **Run 层可重建**：只对真实存在的 `run.accepted` 段生成 Run；启动失败、Resume 失败与断档历史以 `legacy`、`stage` 或 `unknown` 显式标记，并保留原始事件引用。

这样才能满足提案附录 B 中“不伪造缺失的时间和执行状态”的约束。

## 4. 问题二：四个 Runtime 的原生 Session 能力

### 4.1 能力矩阵

| Runtime / 传输 | 新建 | HS 已实现的恢复 | 原生 List | 原生 Inspect | 原生 Delete | 原生 Archive / Fork | HS 持有物 | 真实验证状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Pi 原生 RPC | `--session-dir` 新建 | `--session <file>` | 无原生接口证据 | 无 | 无 | 无 | Pi 格式的 session 文件，位于 HS 的 `sessions/<workerId>` | spawn / resume / 交互已有真实验证 |
| Qoder ACP | `session/new` | `session/load` | `initialize` 声明 `list` | 未声明独立方法 | `initialize` 声明 `delete` | 声明 `fork` / `close` | HS 自己的 `qoder-acp-session.json` 句柄；原生会话在 Qoder 配置根 | create / load / cancel / 审批已真实验证；list / delete / fork / close 未调用、未验证 |
| Qoder stream-json | `--print` 新建 | `--resume <session-id>`，校验返回 ID | 无证据 | 无 | 无 | 无 | 同上，另有 session id | spawn / resume 已真实验证 |
| MCode ACP | `session/new` | `session/load` | 无证据 | 无 | 无 | 无 | `mcode` session 句柄 | create / load / cancel / steer / 审批已真实验证 |
| DSH ACP | `session/new` | `session/resume` | `initialize` 声明 `list` | 无 | 无 | 声明 `close`；无 fork / delete | HS 自己的 session 句柄；原生会话在 DSH 配置目录 | create / resume / cancel / 权限已真实验证；list / close 未调用、未验证 |

说明：

- “声明”不等于“可用”。Qoder 与 DSH 的 `initialize` 返回值只证明 agent 愿意协商这些方法；HS 还没有对方法结果、错误语义、并发访问和会话锁做过真实探测。
- ACP 的 `session/load` 是恢复既有会话并重新附着控制通道；`session/resume`（DSH）要求相同的绝对 `cwd`，且没有历史回放。
- Pi 的 session 文件由 HS 指定目录，因此 HS 可以枚举“自己创建的文件”，但这只能算 HS 本地清单，不能描述为 Pi 原生 Session Discovery。
- Qoder 的 `expectedQoderSessionFile()`（`src/adapters/qoder/launch.ts:271`）说明原生文件路径可由配置根、`cwd` 和 `sessionId` 推导，但这依赖目录约定，不能替代原生 API，也不能证明原生会话未被其他进程占用。
- 所有 Runtime 的 `archive` 都只能先做 HS 管理层归档。没有任何一个运行时的原生 Archive 经过验证。

### 4.2 对 Adapter 接口的含义

提案中的 `SessionCapabilities` 可以保留，但初始值必须严格：

| 能力 | 初始值 | 启用条件 |
| --- | --- | --- |
| `resume` | true（现有能力） | 已满足 |
| `list` | false | 真实调用成功，并明确返回字段、分页、配置根与错误语义 |
| `inspect` | false | 真实调用成功，且能区分“会话不存在”与“配置根/账号不匹配” |
| `delete` | false | 真实删除成功，且失败不会留下半删除状态 |
| `archive` | false | 原生归档语义已验证；否则只提供 HS 层归档 |

### 4.3 结论

0.9 的 Phase H 不能以“ACP 声明了 list/delete”为完成标准。可交付的范围是：

1. 继续使用已验证的 create + resume。
2. 增加 `SessionRef` 与 `runtimeInstanceId`，先解决“同一会话被正确引用”的问题。
3. 逐个 Runtime 做真实能力探测，探测通过后再打开对应能力位。
4. 在能力探测完成前，`session_discover`、`session_delete` 必须返回明确的 `UNSUPPORTED`。

## 5. 问题三：自动 Detach 与 Session Lease

### 5.1 自动 Detach：主体能力已存在

当前终态路径已经做了大部分“释放运行资源”的工作：

| 步骤 | 当前实现 |
| --- | --- |
| 停止接受新操作 | `runtime.finalizing` 与 `isTerminal(record.status)` 守卫 |
| 关闭 Harness 控制会话 | `finalizeSettled` 调用 `session.close({ graceMs })`（`src/supervisor.ts:1769`） |
| 必要时强制清理 | `close` 失败时调用 `forceKill()`（`src/supervisor.ts:1776`） |
| 记录终态 | `run.completed/failed/cancelled` 后写 `worker.exited`（`src/supervisor.ts:1821`） |
| 释放内存对象 | `this.runtimes.delete(record.id)`（`src/supervisor.ts:1847`） |
| 取消路径 | `forceTerminalCancelled` 强制终止并移除 Runtime（`src/supervisor.ts:1680`） |
| 异常退出路径 | `handleHarnessExit` 清理定时器、记录状态并移除 Runtime（`src/supervisor.ts:2087`） |

因此，0.9 的“Worker 完成后自动 Detach”主要是把既有行为显式化，不需要重新实现一套进程回收逻辑。

建议：

- `AttachmentState` 从 `(record.status, runtime 是否存在, finalizing)` 派生，作为读取时视图，不新增第二份持久化状态。
- 需要审计时，只追加 `worker.detached` 事件，事件中的状态与派生结果必须一致。
- `awaiting_input` 不得自动 Detach；现有逻辑本来就会保持进程存活。
- 重复 Detach 的幂等性已有基础：`finalizeSettled`、`handleHarnessExit`、`failStartup` 都用 `finalizing` 或终态守卫；应补 settle/exit 交错、重复 cancel 的回归测试。

### 5.2 Orphaned 是当前最需要先修的安全缺口

`orphaned` 表示“daemon 重启后，PID 仍存活且命令行身份匹配，但 HS 已失去控制通道”（`src/supervisor.ts:301` 起）。它目前被当作终态：

- Retention 会把它列入清理候选（`src/retention.ts:58`）。
- 如果 `includeSessions` 为真，还会删除 `sessions/<workerId>`（`src/retention.ts:85`）。
- 但原 Harness 进程可能仍在运行并继续写文件。

这与提案 §12.4 的结论一致。推荐把 `orphaned` 从自动清理候选中剥离：默认永不自动清理；只有确认 PID 已退出或身份核验为“PID 复用”后，才转换为 `interrupted` / `unknown` 再进入普通清理策略。

### 5.3 Session Lease：范围需要收窄

现有并发保护已经覆盖“同一个 Worker”的控制权：

- `resuming` 集合阻止同一 Worker 的并发 Resume（`src/supervisor.ts:864`）。
- 活跃状态或存在 Runtime 时拒绝 Resume（`src/supervisor.ts:889`）。
- Resume 前检查旧 PID 是否仍属于该 Worker，PID 复用不会被误判为存活（`src/supervisor.ts:929` 起，配合 `src/util/process.ts:51` 的命令行核验）。
- 同一个 `stateDir` 只允许一个 daemon：`src/ipc/daemon-state.ts:20` 的 `daemon.lock` 会检查 PID 存活并清理失效锁。

但是，当前公开 API 不能让两个 Worker 控制同一个原生 Session：每个 Worker 只能 Resume 自己的 `sessionFile`。因此 Lease 在 0.9 的初始范围内不是现有路径的必需组件；它的真实需求来自提案新增的 `session_attach` / 跨 Worker 接管。

可行的范围：

| 范围 | 是否可靠 | 说明 |
| --- | --- | --- |
| 同一 daemon 内的跨 Worker 接管 | 可行 | 进程内互斥 + 原子写入 + `fencingToken` 足够；旧控制者仍受 `resuming` 与 Runtime 守卫约束。 |
| 同一机器、不同 `stateDir` 的同一原生会话 | 不可靠 | `daemon.lock` 按 stateDir 隔离；两个 HS 实例无法看到彼此。需要原生锁或共享锁位置。 |
| 多个 Harness 客户端（如桌面端）与 HS 同时控制同一原生会话 | 未验证 | Qoder / MCode / DSH 的会话级并发语义没有证据；不能用 HS 自己的 Lease 代表原生独占。 |

另外两点：

- Lease 过期不能作为接管依据。必须结合 PID 身份、原生会话可用性和 `fencingToken`；提案在这一点上是正确的。
- `daemon.lock` 目前只检查 `isPidAlive`，没有命令行身份核验。若锁文件 PID 被复用，daemon 可能被错误阻塞。0.9 可以把 `inspectProcess` 用于锁校验，但这属于独立的小修。

### 5.4 结论

- 自动 Detach：可行，且已有 80% 的机制；重点是补显式状态、审计事件和回归测试。
- Session Lease：可行但必须与 `session_attach` 同期实现；初始只承诺单 daemon 范围，跨 stateDir 与原生客户端并发必须明确列为不支持。
- Orphaned 清理保护应优先于 Lease 落地。

## 6. 对提案的修正建议

| 编号 | 建议 | 原因 |
| --- | --- | --- |
| C1 | 把“无损迁移”改为“事件无损保留 + Run 可重建（含 legacy/unknown）” | 启动失败、Resume 失败和断档历史无法从现有事件无损还原。 |
| C2 | AttachmentState 由现有状态派生，不单独持久化 | 避免终态、Runtime 和 AttachmentState 三份真相漂移；审计用事件。 |
| C3 | Session Lease 与 `session_attach` 同期实现，只承诺单 daemon 范围 | 当前 API 没有跨 Worker 会话共享，单独先做 Lease 没有可验证的使用场景。 |
| C4 | 把 `orphaned` 从自动 Retention 候选移除 | 现有 `isTerminal` 会清理仍可能在运行的原生进程。 |
| C5 | 事件白名单必须先定义 `lastProgress` 与输入撤回的兼容方案 | `worker_status.lastProgress` 依赖持久化的 `run.progress`；直接停止保存会让现有外部契约退化。 |
| C6 | Usage 的稳定 ID 保持 `runtime:<workerId>:<seq>`，Run 只作为新增属性 | 改 ID 会破坏现有 Usage 去重、对账和通知兼容。 |
| C7 | Qoder / DSH 的 list / delete / close 在真实探测前保持 false | `initialize` 声明不等于可用；提案附录 B 也要求不伪造能力。 |
| C8 | 不移动现有 `sessions/<workerId>` 目录 | Pi 通过 `--session-dir` 依赖该路径；SessionRef 迁移应先做引用映射，再考虑新目录布局。 |
| C9 | `daemon.lock` 增加命令行身份核验 | 单纯 `isPidAlive` 无法区分 PID 复用；现有 Worker 对账已经有可复用的核验函数。 |

## 7. 建议的 PR 边界

提案的 Phase A–I 内容合理，但建议先做两个独立的小修，再按 A → B/C → D/E → F/G/H/I 推进。小修不改变架构，只消除已确认的安全与启动成本问题。

### PR 0：Orphaned 保护与锁身份核验（独立，优先）

- Retention 默认不自动清理 `orphaned`。
- 对账确认 PID 已退出或 PID 复用后，转换为 `interrupted` / `unknown`。
- `daemon.lock` 使用进程身份核验。
- 回归测试：orphaned 不进入清理候选；dry-run 结果稳定；PID 复用不再阻塞合法启动。

退出标准：`npm run build`、相关单元/集成测试通过；不涉及真实 Harness。

### PR 1：启动性能与增量消费者（Phase E 的最小子集）

- 为每个 Worker 持久化事件消费检查点（Lifecycle / Metrics / Notification 各自独立）。
- `Store.init()` 保留事件缓存与索引，但不再让 Metrics 与 Notification 重扫全部历史。
- 增加只读的 `storage` 诊断或启动计时日志。
- 合成 1,000 Worker / 10,000 事件的基准，记录升级前后冷启动。
- 先保留现有 `run.progress` 事件，白名单放到后续 PR，避免破坏 `lastProgress`。

退出标准：冷启动不再随已消费历史线性增长；通知与 Usage 不重复创建；断档历史仍能报错。

### PR 2：身份模型（Phase A + F 的只读部分）

- 新增 `RunRecord`、`SessionRef`、`WorkerSnapshot` 类型与派生器。
- 新事件可选携带 `runId`；旧事件不改写。
- 迁移器只把真实 `run.accepted` 段生成 Run；启动失败、Resume 失败标记 `legacy`。
- Task 统计优先读取 Snapshot，缺失时回退到现有 Worker 聚合并标记 `legacy`。
- 保持现有 CLI / MCP / IPC 返回字段兼容。

退出标准：旧状态目录可加载；Run / Snapshot 与现有 Timeline 对照一致；不重编号 `seq`。

### PR 3：Session 接管与 Lease（Phase B/C 的受控子集）

- 只在同一 daemon 内支持把既有 `SessionRef` 关联到新 Worker。
- 实现 `SessionLease`、`fencingToken`、原子获取/释放。
- 接管前必须核验旧控制者已退出；过期不自动接管。
- 跨 stateDir 与原生客户端并发明确返回 `UNSUPPORTED`。
- 真实能力探测通过后，再逐个打开 `SessionCapabilities`。

退出标准：双 Worker 并发接管被拒；旧 Worker 无法继续控制；daemon 重启后 Lease 状态可对账。

### PR 4：结果存储与统一维护

- Result Store 去重最终文本，Worker 只保留 `resultRef`。
- Maintenance Service 统一 Worker / Event / Notification / Idempotency / Usage / Result 清理。
- 所有清理支持 dry-run、审计和失败重试。
- Orphaned、活动 Lease、未 ACK 通知、Pin 的 Session 默认受保护。

退出标准：清理前后引用完整；被保护的记录不减少；失败可重试。

## 8. 验收与证据要求

| 类别 | 需要补的验证 |
| --- | --- |
| Run 迁移 | 用真实旧状态目录生成 Run 对照表；覆盖正常完成、失败、取消、启动失败、Resume 失败、断档历史。 |
| 启动性能 | 合成 1,000 Worker / 10,000 事件，记录 Store、Metrics、Notification 和总启动耗时；与 0.8.0 对照。 |
| 事件压缩 | 压缩后 `seq` 不重编号；通知 ID 不变；人为截断仍能检测；被压缩造成的缺口不被误报为损坏。 |
| Session 能力 | 每个 Runtime 单独做真实探测：list、inspect、delete、close 的返回、错误和并发语义。未通过的能力保持 false。 |
| Lease / Detach | 重复 Detach、settle/exit 交错、取消与完成并发、双 Worker 接管、daemon 重启、PID 复用。 |
| Retention | Orphaned 不自动清理；活动 Lease 保护；未 ACK 通知保护；dry-run 不修改数据。 |

文档与证据必须区分：

- 真实验证：真实 Harness 进程与桌面端行为。
- 协议验证：假 Harness 或 ACP 报文。
- 静态检查：代码与类型层面的事实。
- 未验证：仅有声明或设计。

## 9. 本轮未验证的内容

- Qoder `session/list`、`session/delete`、`session/fork`、`session/close` 的真实行为。
- DSH `session/list`、`session/close` 的真实行为。
- Pi / MCode 是否存在可用的原生 Session 枚举或删除接口。
- 多个 HS `stateDir` 或多个客户端同时访问同一原生 Session 的并发语义。
- 大状态目录下增量消费者与事件白名单的实际加速倍数。

这些项目在对应 PR 开始前必须有真实探测或明确的 `UNSUPPORTED` 结论，不能只依据 `initialize` 声明。

## 10. 最终结论

0.9 的核心职责划分可以作为下一阶段基线，但实施顺序需要两个调整：

1. 先修 `orphaned` 清理与锁身份核验，这是当前代码已经存在的数据安全问题。
2. 再做增量消费者，解决启动成本；身份模型随后落地，Lease 与 `session_attach` 绑定。

完成这些之后，0.9 的“多 Harness、多 Session、多 Worker 编排”才有可靠的边界。当前代码已经具备进程生命周期、事件持久化、通知、用量和单 daemon 控制的基础；0.9 的主要工作是拆分身份、减少无必要历史、明确原生能力边界，而不是重写 Harness 或引入新的存储后端。
