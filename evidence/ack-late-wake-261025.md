## 已有事实

同一 Worker 的两个独立完成事件：

| 事件 | 创建（北京时间） | CLI 接受回执时间 | ACK | 聊天回合开始（秒精度） |
| --- | --- | --- | --- | --- |
| #445 | 10/25 01:54:42.092 | 01:54:43.654 | 02:01:46.426 | 02:02:42 |
| #714 | 10/25 04:30:07.857 | 04:30:09.369 | 04:43:56.733 | 04:44:46 |

每条都是 pending → delivered → 带 ackAt 的 delivered，attempts=1，并有单一队列 messageId。未见事件窗口内 Daemon/Desktop 重启证据。ACK 后约 55.6s / 49.3s 才出现对应聊天消息；聊天时间只有秒精度，不能据此给出更精确延迟。

这支持“单次已接受队列消息晚到”，不支持“HS 重复创建或重投”结论。#360/#445/#626/#714 不能因 Worker ID 相同而合并。原始 UI consumedAt、排队内部调度点仍未知。

## 作用边界

HS 0.4.3 入队前再次检查 ACK 是正确但不足的：两例中，ACK 都发生在成功入队数分钟之后。公开 CLI 帮助和当前官方开发命令文档没有提供按回执 ID 撤销队列的命令。本次不写 Codex 私有队列文件，不将杀 CLI 等同撤回接受过的消息，不靠任意增大延迟宣称解决。

0.4.4 增加可选原生 UserPromptSubmit 消费闸门，真正将检查放到下一次模型提交前；增加按需投递时序诊断。部署、回退、信任确认和限制见 [codex-ack-gate.md](../docs/codex-ack-gate.md)。

- 模拟队列稳定复现：只接受一次，之后 ACK，持久化仍 delivered/attempts=1；消费前闸门读取同一记录并拒绝旧指针。重启不会重试 ACK 通知。
- 原生测试：本机 CLI 0.161.0，真实 TUI + 真实 queue，本机模型端替身、隔离 HS 通知夹具。入队 #445 后 ACK，再释放正在进行的回合，消费 hook 判定 block；已 ACK 消息模型请求数为 0。新 #714 未 ACK，判定 allow 且模型端收到请求。
