## 2. Codex 唤醒等级：**A 级已单次验收**，B 级仍是通用形态

明确结论，不含糊：

- **本轮实际完成的是 B 级**：由外部探针管理的真实 `codex app-server` 会话，通过 HS 的 `codex-queue` 通道在回合结束后被自动唤醒并读取 Worker 结果（`evidence/codex-wake-e2e/result-late-worker.json`）。
- **A 级已完成一次真实桌面验收（2026-10-22，交付后补测）**：在用户桌面会话中，回合于 Worker 完成前结束；`codex queue` 投递后同一 thread 自动开始新回合并读取结果（`evidence/desktop-wake-1022/`，含原始截图）。这证明桌面端在该次运行中保持了 thread 加载；只有一次成功运行，不能据此推断长期稳定性，也未测量精确唤醒延迟。
- **C 级兜底始终可用**：默认通道是无外部依赖的本地收件箱（`supervisor_notifications`），不依赖宿主加载状态，也不含隐藏轮询。
- 实验中使用的认证：沿用当前 ChatGPT 登录；两轮 Codex 对话的额度消耗未单独计量。

## 9. 仍存在的技术边界与下一步建议

1. **A 级桌面唤醒仅单次验收**：2026-10-22 的桌面测试已通过（`evidence/desktop-wake-1022/`）。仍需注意：它依赖宿主保持 thread 加载；若桌面端卸载 thread，消息会留在队列直到再次加载。建议后续做重复稳定性验证（多通知、忙碌/离线、长摘要）。
2. **Qoder steer/follow-up 未生效**：当前 `priority:"next"/"later"` user 消息被 CLI 接受但未影响运行；下一步应定位 Qoder 官方的异步消息入口，而不是继续猜测。
3. **Qoder allow/deny 未触发**：需要在能产生 `can_use_tool` 的工具/版本上重试。
4. **Qoder 静默窗口**：窗口内合并、窗口外早判定已由确定性测试固定；若真实 CLI 出现长间隔多 result，仍可能提前判定完成。
5. **投递语义是 at-least-once**：不承诺 exactly-once；已确认记录不会重发，但崩溃窗口可能产生重复消息。
6. **PID 身份依赖命令行可读**：读取失败时回退为保守的 `orphaned`；token 偶然匹配概率极低但非零。
7. **`prune` 是显式操作**：没有自动归档；删除 Worker 目录会失去 resume 能力（默认保留 session 文件）。
8. **SSH 科研场景未验证**：需真实远程主机；HS 只管理 Worker 进程，不管理 SSH 连接与远程作业生命周期。
9. **单用户本地 daemon**：无多用户隔离；`cwd` 不是沙箱。

## 验收对照（最重要的标准）

> 长任务正常运行时，不需要 GPT 定期参与无价值的状态检查；重要事件能够可靠保存，并通过宿主真实支持的渠道及时交付；整个系统仍保持轻量。

- 重要事件保存：✅ 稳定 ID 通知、崩溃可重建、确认后不重复。
- 被动轮询需求：✅ 收件箱可一次拉取；可选 `codex-queue` 在 B 级/A 级机制上实现事件驱动下一回合。
- 轻量：✅ 无新增依赖、无额外服务、默认零外部调用。
